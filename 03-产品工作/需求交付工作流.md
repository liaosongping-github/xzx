# 需求交付工作流

> 一张 REQ 卡片 = 需求澄清权威源（池表只索引）。  
> 标准顺序：**待处理 → 处理中（澄清）→ 设计草案确认 → 原型 → PRD → 评审中 → 开发中 → 已上线**。

## 1. 流转总览

入池（飞书表 + 本地 REQ）走个人 Skill `requirement-pool-sync`：先映射表确认再写；默认不加描述/方案列。

```text
需求池登记（待处理）
    ↓
REQ 澄清写满并确认（处理中）
    ↓
设计草案（待确认区/产品方案 → 确认后落 03-产品工作/方案/）
    ↓
原型（双引鲸高保真 / 其他可低保真）
    ↓
PRD（规则与验收写全）
    ↓
评审中 → 开发中 → 已上线
```

| 阶段 | 需求池状态 | 通过门禁 |
|---|---|---|
| 登记 | 待处理 | 有编号、来源、一句话问题 |
| 澄清 | 处理中 | REQ 背景/目标/范围/方案大方向/待明确问题已写；负责人确认可进入方案 |
| 方案 | 处理中 | 设计草案确认落库（或明确「本需求跳过草案」） |
| 原型 | 处理中 | 可评审原型 + README 挂回 REQ |
| PRD | 处理中 → 评审中 | PRD 草稿完成且挂回 REQ；进入评审时改「评审中」 |
| 开发 | 开发中 | 评审通过；提测后仍保持开发中直至上线 |
| 上线 | 已上线 | 填上线时间 |

支线：`暂缓`（任意阶段可挂起，原因写在 REQ 变更记录）。

## 2. 文档职责对照

| 维度 | REQ（澄清权威源） | 设计草案 | 原型 | PRD |
|---|---|---|---|---|
| **一句话定位** | 为什么做、做成什么样（大方向） | 怎么做（方案选型与结构） | 长什么样、怎么点 | 做成什么才算过（可开发） |
| **路径** | `03-产品工作/需求/REQ-*.md` | 草案：`00-待确认区/产品方案/`；正式：`03-产品工作/方案/` | `03-产品工作/需求原型/` 或 `原型/` | `03-产品工作/PRD/PRD-*.md` |
| **必须写** | 来源；背景；目标；范围（内/外）；方案概要（大方向）；验收标准（粗）；依赖与风险；待明确问题；相关文档链接 | 目标与成功标准；方案选型及不采用项；菜单/权限/信息架构；关键交互原则；数据粒度；本期不做 | 页面结构；主路径交互；关键态（空/错/权限等按规范）；与现网/字段字典差异说明 | 用户与场景；业务流程；功能范围；页面与交互（可链原型）；业务规则表；异常与边界；数据与埋点（若需要）；验收标准（细）；未决问题 |
| **不要写** | 逐字段规则、逐页控件说明、完整交互细节 | 完整验收用例、研发排期细节 | 长篇业务论证、替代方案辩论 | 重复粘贴整份知识库；与 REQ 冲突且不回写的口径 |
| **读者** | 产品自己 / 业务拍板人 | 产品 / 设计 / 关键研发 | 业务确认 / 产品 / 前端 | 研发 / 测试 / 评审会 |
| **与池表关系** | 池表一行只索引；正文只维护在 REQ 文件 | 不进池表；REQ「相关文档」回链 | 不进池表；REQ / PRD 回链 | 池表「关联 PRD」填链接 |

### 反双写规则

1. **背景 / 目标 / 范围边界**：以 REQ 为准；PRD、草案只摘要并链接 REQ，不另起冲突口径。
2. **方案选型（为何选 A 不选 B）**：以设计草案为准；REQ 只保留一句方案概要。
3. **字段、状态、权限细则**：以知识库（字段字典等）+ PRD 业务规则为准；原型只演示，不充当权威枚举源。
4. **发现冲突**：先改权威源，再改下游；并在 REQ 变更记录记一笔。

## 3. 各阶段输入上下文（给 Agent / 自己）

| 产出 | 必读上下文 | 可选 |
|---|---|---|
| REQ 澄清 | 需求池条目意图；相关会议/调研；`06-长期记忆/待确认问题.md` 中相关项 | Raw 索引摘要 |
| 设计草案 | **已确认的 REQ**；相关 `02-业务知识库` 条目（**按主题钉选，不整库塞入**） | 竞品/旧方案 |
| 原型 | REQ + **已确认草案**（或 REQ 方案概要且已声明跳过草案）；双引鲸须加 [设计规范/双引鲸](设计规范/双引鲸/README.md)；相关字段字典 | 摹客交互参考 |
| PRD | REQ + 草案 + 原型 README + 钉选知识库条目 + 仍开放的待明确问题 | 决策记录 DEC |

禁止：把整个 `02-业务知识库/` 当默认上下文；未验证材料不得写成已验证事实。

## 4. 确认门禁（与待确认区对齐）

| 产物 | 确认要求 |
|---|---|
| REQ 澄清结论 | 廖送平确认「可进方案/原型」后再开重活 |
| 设计草案 | 先进 `00-待确认区/产品方案/`，确认后落 `03-产品工作/方案/` |
| 知识库增量 | 先进 `00-待确认区/知识候选/`，确认后落 `02/` |
| 原型 | 产品内部确认 →（需要时）业务确认 → 再冻一版给 PRD |
| PRD | 评审前至少产品确认；评审通过后需求池改「评审中」或进入「开发中」按会议结论 |

## 5. 回写与闭环

- 原型/PRD 过程中新结论：**回写 REQ**（范围变化、目标变化必须记变更记录）。
- 可沉淀的业务事实：**经待确认区**进知识库，不把 PRD 当知识库。
- 重要取舍：可另建 `05-决策记录/`，并在 REQ / PRD「相关文档」链接。

## 6. 可跳过情形（须在 REQ 写明）

| 情形 | 可跳过 | 不可跳过 |
|---|---|---|
| 文案/配置类小优化 | 设计草案、高保真原型 | REQ 澄清、PRD（可极简） |
| 纯规则/后端逻辑、几乎无 UI | 高保真原型 | REQ、草案或等价方案说明、PRD |
| 演示/探索 | 正式 PRD | 仍建议有 REQ 卡片标明「演示」 |
