# 双引鲸可视化原型复刻与 Agent 协同平台
## Master Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> 本文是本项目唯一的总实施计划与执行进展权威。必须先完成知识库目录调研、现网全量普查、逐页取证和架构确认，再开始对应页面编码。禁止未访问目标现网页面就凭模板、旧截图、字段字典或记忆制作页面；禁止跳过 Registry / Schema 基础设施。所有功能必须可测试、可验证，并保持后续 Visual Editor 和 Agent 可持续扩展。

**Goal:** 以双引鲸贸易端现网为唯一视觉与交互标准，1:1 复刻当前账号可见的完整 Web 系统；页面数据可脱敏并静态化，但页面、字段、功能、样式、布局、状态和操作路径不得因使用 Mock 而删减。

**Architecture:** 先用知识库菜单树建立覆盖基线，再逐入口访问现网，形成页面—状态—字段—交互—视觉证据包；页面只能在证据包通过开工门禁后进入 Schema、Registry、组件、Mock 和 Renderer 实现。产品资料是首个校准样板，验收后按一级模块分批扩展，所有页面最终由同一套 Schema 驱动运行、编辑和验证。

**Tech Stack:** React + TypeScript + Vite；Registry / Schema / Renderer；静态 Mock Runtime；Playwright 只读采集与本地 E2E/截图对比；Git 版本管理。

**Spec:** `09-提示词/现网页面复刻.md`、`03-产品工作/设计规范/双引鲸/README.md`、`02-业务知识库/系统与流程/双引鲸ERP/07-菜单树.md`。

### “1:1 复刻”的强制定义

本计划中的“复刻”不是相似风格、组件示例或静态截图，而是在约定视口与当前账号权限下达到以下一致：

1. **信息架构一致**：登录后的全局壳、一级/二级菜单、菜单顺序、图标、展开态、面包屑、多页签、路由和页面间跳转一致。
2. **页面内容一致**：每个入口的页面类型、标题、页签、字段名称与顺序、控件类型、占位符、默认值、必填标识、按钮、表格列、操作列、分页和提示文案一致。
3. **视觉一致**：颜色、字体、字号、字重、间距、尺寸、对齐、边框、圆角、阴影、固定/滚动区域、遮罩、层级和响应式表现一致；不能仅做到“使用相同蓝色”。
4. **交互一致**：菜单、页签、查询/重置、排序、筛选、分页、列设置、勾选与批量操作、新建、查看、编辑、删除、更多操作、弹窗、抽屉、确认框、提示、返回和跨页跳转均可操作，触发条件与反馈一致。
5. **状态一致**：至少覆盖默认、悬停、聚焦、选中、禁用、加载、空数据、校验失败、操作成功/失败、无权限和危险操作确认；只复刻默认首屏不算完成。
6. **数据边界**：允许使用脱敏静态数据和本地 Mock CRUD 代替真实后端；不要求复刻真实接口、权限计算、文件解析、打印引擎和业务公式执行，但对应入口、表单、过程界面、状态反馈及本地可演示结果必须保留。
7. **证据优先**：现网当前实装是唯一验收标准；知识库用于建立目录和业务索引，旧截图、设计规范、字段字典用于辅助，不得覆盖当次现网观察。

任何因安全或技术边界不能做到 1:1 的项目，必须逐项写入“豁免清单”，包含现网行为、原型替代行为、原因、影响和廖送平确认；未登记豁免不得自行简化。

# 1. 项目目标

构建一个高度复刻“双引鲸”后台系统的可运行 Prototype Platform。

最终系统必须同时支持：

1. 高度还原双引鲸页面、布局、组件、交互和页面流程。
2. 使用 Mock 数据完成完整交互。
3. 非程序员通过 Visual Editor 修改页面。
4. 所有页面和组件采用 Schema 驱动。
5. 使用 Registry 管理页面、组件、动作、数据、设计规范和资源。
6. 建立可复用 Component Library。
7. 建立 Design System。
8. 支持页面版本、保存、回滚、Undo/Redo。
9. 支持 Playwright 对原系统与复刻系统进行自动化验证。
10. 后续支持 Agent 通过自然语言修改/生成页面。
11. 人工 Visual Editor 与 Agent 必须修改同一套 Schema，禁止形成两套互相独立的页面体系。

# 2. 核心架构

```text
Agent → Registry 中心（Page / Component / Action / Data / Design / Asset）
      → Page Schema → Component Tree → Visual Editor / React Renderer
      → Prototype Runtime → Playwright Tests
```

# 3. 架构原则

## 3.1 Schema First

页面不能依赖硬编码 JSX 作为唯一事实来源。Page 必须可描述 `layout`、`components`、`props`、`dataBindings`、`actions`、`metadata`，React Renderer 根据 Schema 渲染页面。

## 3.2 Registry First

系统中的页面、组件、Action、数据、设计 Token、资源都必须可注册、可查询。Registry 是 Agent 和 Visual Editor 访问系统结构的统一入口。

## 3.3 Single Source of Truth

Visual Editor、Agent、开发代码 / Registry 都操作同一份 Schema。禁止编辑器、Agent、React 页面各维护一套数据。

## 3.4 原系统和复刻系统分离

双引鲸原系统只作为 Observation / Reference。复刻系统拥有自己的页面、Schema、Component、Mock Data、Action 与 Design System，且不得直接依赖原系统运行。

# 4. 技术路线

```text
React + TypeScript + Vite
Visual Editor：Puck / Craft.js + dnd-kit
UI：按双引鲸实际视觉体系组件化，不复制截图
Mock：MSW 或等价方案
Documentation：Storybook
E2E：Playwright
Version：Git
Schema：TypeScript + JSON Schema / 等价校验方案
```

具体库版本必须在项目勘察阶段确认当前稳定版本，不允许盲目使用过时依赖。

# 22. 关键验收标准

- **范围**：冻结版目录中全部现网可见叶子入口、子页和已取证状态均已核销；不能用“页面可打开”替代页面完整验收。
- **1:1**：页面、字段、功能、样式、布局、文案、状态和操作路径逐清单对照现网一致；静态数据不构成删功能理由。
- **证据**：每页有当次现网证据包、同视口对照结果、差异关闭记录和验收结论。
- **Registry**：可查询系统页面、页面组件、组件使用页面和按钮 Action。
- **Visual Editor**：无需代码可改文字、字段、列、按钮、弹窗、跳转和组件位置。
- **Runtime**：修改后页面正常运行。
- **Version**：可保存、预览、发布、回滚。
- **Agent**：修改 Schema 后页面自动更新。
- **Validation**：非法 Schema 不允许保存。
- **E2E**：核心页面的原系统与复刻系统操作流程一致。

# 23. 开发规则

1. 不允许跳过 Registry。
2. 不允许为了快速完成页面而大量硬编码。
3. 不允许 Visual Editor 单独维护另一套页面数据。
4. 不允许 Agent 直接绕过 Schema 修改 UI。
5. 公共组件必须优先进入 Component Registry。
6. 新增业务组件前先判断是否可以复用已有组件。
7. 修改公共组件前必须检查 Dependency Graph。
8. 每完成一个阶段必须运行对应测试。
9. 不允许用截图伪造交互。
10. 不允许使用真实后端作为第一阶段依赖。
11. 所有页面必须能够独立通过 Mock Runtime 运行。
12. 所有重要结构必须有 TypeScript 类型。
13. 所有 Schema 必须可验证。
14. 所有重要修改必须可以回滚。
15. 不要为了“未来可能需要”提前实现大量复杂功能。

# 24. 开发优先级

```text
P0：Registry / Schema / Renderer / Component System
P1：产品资料单页复刻 / Mock Runtime / Design System / 最小 Visual Editor
P2：扩展页面复刻 / 完整 Visual Editor / Undo-Redo / Version / Preview-Publish
P3：Dependency Graph / Audit Log / 自动化验证
P4：Agent / Agent Page Generation
```

不要一开始就开发 Agent；先把底层系统建设好，Agent 才有可靠的操作对象。

# 25. 每个阶段的完成条件与推进门禁

每个 Phase 必须同时满足：代码完成、测试通过、页面可运行、Schema 有效、Registry 正确、文档完成。不能以“代码写完了”作为阶段完成标准。

此外，必须完成本计划“阶段门禁”规定的测试、检查和廖送平确认。未取得“确认进入下一 Phase”的明确结论，任何后续 Phase 只能保持待开始，不得实施。

# 26. 最终用户体验

正常模式下像普通后台一样使用。编辑模式下点击页面和组件，在右侧修改属性，预览、保存版本并发布。未来可直接告诉 Agent“增加一个客户等级筛选条件”，由 Agent 修改 Schema、自动验证、生成新版本，用户确认后发布。

# 27. 最终成功标准

1. 冻结版目录中的全部现网可见页面及其已取证子视图、弹层和状态完成复刻，没有遗漏入口。
2. 页面、字段、功能、样式、布局、文案与交互路径按清单 1:1 对齐；仅数据源允许用脱敏静态 Mock 替代。
3. 每页均有现网证据、逐项验收、视觉对照、E2E 与差异归零/已批准豁免记录。
4. 用户无需代码修改页面文字。
5. 用户无需代码增加、删除、调整表格字段。
6. 用户无需代码修改按钮行为或增加弹窗。
7. 用户可以保存、预览、发布、回滚。
8. Agent 可以根据自然语言修改已有页面，并根据现有组件和 Design System 创建新页面。
9. 系统可以自动验证复刻页面与双引鲸原系统的关键行为。

# 29. 项目最终形态

```text
Agent → Natural Language → Registry
Registry（Page / Component / Action / Data / Design / Asset / Dependency / Version / Audit）
                         ↓
                      Schema
                ↙                 ↘
        Visual Editor           React Renderer
                ↘                 ↙
                 Prototype Runtime
                         ↓
            Playwright Validation → Version / Publish
```

最终目标不是复制一个双引鲸页面，也不是只建立一套空的平台基础设施，而是先交付与当前双引鲸贸易端 1:1 的完整可交互原型，再让这套原型能够持续编辑、复用、验证并由 Agent 迭代。
