## 1）菜单结构 —— 用哪些工具

| 工具 | 作用 |
|------|------|
| `browser_navigate` | 打开 `https://trade.tsbsoft.com/tsHome` |
| `browser_wait_for` | 等首页/菜单渲染完（或等关键文字出现） |
| `browser_snapshot` | 拿整页可访问性树，识别侧栏 `tree` / `menuitem` / `link` |
| `browser_hover` / `browser_click` | 展开折叠的一级/二级菜单 |
| `browser_evaluate` | 批量扫 DOM：菜单文字、层级、`href`、菜单编码 |
| `browser_network_requests` + `browser_network_request` | 若菜单来自接口（常见），直接解析菜单 JSON，比点开更全更稳 |

**产出形态（示例）**

```text
  ├─ 采购入库单
销售管理

  └─ ...
```

若登录页挡住：用 `browser_snapshot` 找账号/密码框 → `browser_fill_form` / `browser_type` → `browser_click` 登录；有弹窗再用 `browser_handle_dialog`。

## 2）有哪些单据 + 单据全部字段

分两步：**先盘点单据清单，再进每个单据抽表头字段**。

### 盘点单据

| 工具 | 作用 |
|------|------|
| `browser_click` | 按菜单逐个进入“单据列表页” |
| `browser_find` | 快速搜“新增 / 新建 / 单据”等入口，不必每次全量 snapshot |
| `browser_evaluate` | 从列表页标题、Tab、路由、菜单名汇总单据清单 |
| `browser_network_*` | 抓菜单/权限/模块配置接口，交叉核对“系统里有哪些单据” |

### 抽单据表头字段

进入「新建」或「编辑」页后：

| 工具 | 作用 |
|------|------|
| `browser_snapshot` | 识别 `textbox` / `combobox` / `checkbox` / `datepicker` 等 |
| `browser_evaluate` | 扫 label、placeholder、`name`/`formControlName`、必填标记、只读态、Tab 分区 |
| `browser_click` | 点开「更多信息 / 高级 / 其它」折叠区，避免漏字段 |
| `browser_take_screenshot` | 复杂布局时做人眼核对，不当主数据源 |

字段信息建议结构化为：`字段名 / 控件类型 / 是否必填 / 是否只读 / 所属分区 / 默认值提示`。

## 3）单据明细字段（行项目 / 明细表）

明细通常在表格（ag-Grid / Element Table / 自研 grid）里，常要滚动、点“增行”、看列设置。

| 工具 | 作用 |
|------|------|
| `browser_snapshot`（可对表格区域） | 看表头列名、操作列 |
| `browser_scroll` / `browser_hover` | 横向滚出被挡住的列 |
| `browser_click` | 点「列设置 / 显示列 / 增行 / 编辑行」 |
| `browser_evaluate` | 抽 `th`、列配置、`data-field`、grid API 的 `columnDefs` |
| `browser_network_*` | 打开明细编辑时抓 schema/字典/保存接口，拿到界面未展示的隐藏列 |
| `browser_run_code_unsafe` | 仅当上述不够用时：写一小段 Playwright 脚本循环点菜单、等表格、导出列定义（慎用，权限高） |

明细字段建议单独列表：`列名 / 字段键 / 类型 / 可编辑 / 是否合计列 / 是否必填`。

## 推荐执行顺序（落地时）

```text
navigate → wait → (登录) → snapshot
  → evaluate/network 抽菜单树
  → 逐菜单 click 进列表
  → click 新建/编辑
  → evaluate 抽表头字段
  → 定位明细表 → evaluate/network 抽列
  → 下一张单据 … 直到菜单走完
```

核心组合其实就这几类：

1. **导航与等待**：`browser_navigate`、`browser_wait_for`、`browser_tabs`  
2. **定位与操作**：`browser_snapshot`、`browser_find`、`browser_click`、`browser_hover`、`browser_type`/`browser_fill_form`  
3. **批量抽取**：`browser_evaluate`（主武器）  
4. **补全隐藏字段**：`browser_network_requests` + `browser_network_request`  
5. **复核**：`browser_take_screenshot`  
6. **兜底脚本**：`browser_run_code_unsafe`

## 哪些最吃 token

| 操作 | 消耗程度 | 原因 |
|------|----------|------|
| 全页 `browser_snapshot` | 很高 | 整棵无障碍树很长，尤其 ERP 侧栏+多 Tab+表格 |
| 每次操作后再全量 snapshot | 很高 | 点菜单 × N 次 = N 份大树 |
| `browser_evaluate` 返回整页 HTML / 超大 JSON | 很高 | 结果整段进上下文 |
| `browser_network_request` 拉完整 response body | 中高 | 配置/字典接口可能很大 |
| `browser_take_screenshot` | 中等 | 图片要视觉理解，也会占上下文 |
| 只 `click` / `wait` / 小范围 `find` | 较低 | 返回短 |

粗算：若有 30 个菜单、每个单据新建页再全量 snapshot 2～3 次，对话里很容易堆到**几十万级 token 量级**（视页面复杂度而定），贵且容易顶满上下文。

## 怎样明显省 token

1. **少用全页 snapshot**：定位用 `browser_find` 或带 `target`/`depth` 的局部 snapshot。  
2. **主抽数用 `browser_evaluate`**：只 `return` 精简 JSON（菜单名+层级、字段名+类型），禁止把整页 DOM 打回来。  
3. **能走接口就走接口**：菜单/表单 schema 若在 API 里，一次 network 解析往往比点 50 个页面省一个数量级。  
4. **分批做**：先菜单清单 → 再 1～2 张样板单据 → 再按模块扫；不要一个会话里全站扫完。  
5. **截图只做抽检**，不当主数据源。  
6. **结果落盘到工作区文件**（Agent 模式），后续会话读文件，而不是反复把同一份树贴回聊天。

## 结论

- **按“每页全量 snapshot 点一遍”**：很吃 token。  
- **按“evaluate 抽精简结构 + 必要时看接口 + 分批”**：可控，通常比纯人工点开抄字段仍划算。

若你只是先摸清结构，建议第一轮目标收窄成：**只要菜单树 + 单据名称列表**，字段表第二轮再按优先级做，token 会少很多。
