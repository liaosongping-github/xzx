## 这样做的目的（我的判断）

核心是：**让产品产出建立在已沉淀、可追溯的业务认知上，而不是每次从聊天/记忆/零散印象重写。**

更具体一点：

1. **降低幻觉与口径漂移**  
   PRD/需求里的流程、状态、字段、角色，应对齐 `02` 里已有条目（哪怕仍是「待验证」），而不是 Agent 或个人临时复述。

2. **形成「学→用」闭环**  
   入职熟悉期大量材料先进 `02`；做需求/优化/方案时再回灌到 `03`，避免知识库只堆积、产品文档另起炉灶。

3. **暴露缺口而不是掩盖缺口**  
   写 03 时若 `02` 不够，应显式登记待确认问题，而不是用模糊表述硬写方案。

4. **跨 Agent / 跨会话可复用**  
   权威在 Markdown；下一次做相关需求时，先读同一批知识条目，而不是翻聊天。

5. **区分「知识」与「产品决策」**  
   `02` 沉淀「业务/系统是什么」；`03` 沉淀「我们要改什么、做成什么」。结合产出，不是把两者混成一份文件。
