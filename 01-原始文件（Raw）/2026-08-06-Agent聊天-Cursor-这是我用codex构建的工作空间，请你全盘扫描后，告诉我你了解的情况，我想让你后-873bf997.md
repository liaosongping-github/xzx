## 实际怎么跑

Codex 当时装的是两层东西：

2. **本机 Node 常驻进程**（[`start-raw-automation.ps1`](08-自动化/start-raw-automation.ps1)）
   - `raw-pipeline.mjs watch`：盯 `01-原始文件（Raw）`
   - `lark-minutes-bridge.mjs watch`：盯飞书妙记

触发条件是「你登录 Windows / 到点 / Raw 目录有新文件」，不是「打开了哪个 Agent」。

```text
Windows 登录
  → 计划任务
    → start-raw-automation.ps1
      → node raw-pipeline (常驻)
      → node lark-minutes (常驻)
        → 有待消化资料时再调用 codex exec 做提炼
```

所以：**Cursor 里写作 ≠ 自动化停了；Codex 没开 ≠ 扫描停了。** 只要本机任务和 worker 还在，两边都一样。

## 「Codex」在这里扮演什么角色

容易混淆的一点：名字里的 Codex 有两种含义。

| 角色 | 是什么 | 和 Cursor 的关系 |
|---|---|---|
| **调度/采集** | 计划任务 + Node watch | 与 IDE 无关，Cursor/Codex 都一样 |
| **消化引擎** | `raw-pipeline` 里 `spawn` 的 `codex exec` | 后台子进程，不要求你开 Codex 聊天窗 |

也就是说：自动化是「本机脚本」；Codex CLI 只是消化时调用的工具。你在 Cursor 里改文件、进 Raw，照样会被同一条 pipeline 扫到。

---

## 计划里「聊天入库」如何保证两边都吃到

按现有设计，会再加第三个 worker（`agent-chat-bridge`），同样由 `start-raw-automation.ps1` 拉起，并挂进登录自启。

- **Cursor 聊天**：读磁盘上的 `agent-transcripts/*.jsonl` → 写成 Raw  
- **Codex 聊天**：读 `~/.codex/sessions/*.jsonl`（按 `cwd` 过滤本工作空间）→ 写成 Raw  
- 之后仍走同一个 `raw-pipeline`

两边都是「读落盘文件」，不是「嵌在 Cursor/Codex 应用内的插件」。只要会话会写到本机、worker 在跑，就能入库。

---

## 什么情况下会「在 Cursor 上不自动」

不是 Cursor 专属问题，而是本机链路断了：

1. 计划任务被删/禁用，或登录后 worker 没起来  
2. Node / `codex` CLI 不在 PATH，或只用了 Codex 自带 runtime（脚本已尽量避开）  
3. 飞书 / Codex 登录态过期（影响妙记同步或消化，不影响「扫本地 Raw」本身）  
4. 聊天桥未安装进 launcher 前，Cursor 聊天不会自动变 Raw（这是计划要做的部分）

自查可以看：

- 任务计划程序里上述两个任务是否还在  
- `08-自动化/.runtime/*.pid` 对应进程是否存活  
- `08-自动化/.runtime/*.log` 是否有近期心跳/扫描记录  

---

**一句话**：不是「让 Cursor 继承 Codex 的自动化」，而是「自动化本来就独立于 Agent；Cursor 只是另一个使用者，读写的是同一套工作空间和同一套本机 worker」。构建聊天桥时，也会按同样方式挂到现有 launcher，而不是做成 Cursor-only 功能。
